## What Counts as the Same Origin

Origin = scheme + host + port. Starting origin: `https://app.example.com`

| URL | Same origin? | Why |
| --- | --- | --- |
| `https://app.example.com/users` | Yes | Path doesn't matter |
| `https://app.example.com/login` | Yes | Same scheme/host/port |
| `https://api.example.com` | No | Different host |
| `http://app.example.com` | No | Different scheme |
| `https://app.example.com:8443` | No | Different port |
| `https://example.com` | No | Different host |

## Why the Browser Cares: Same-Origin Policy

If you're logged into `bank.com`, your browser holds its auth cookie. Visiting `evil.com` shouldn't let that page read `bank.com`'s data using your cookie. The **Same-Origin Policy (SOP)** is the browser boundary that stops a page from freely reading responses from a different origin.

## SOP Doesn't Mean Cross-Origin Requests Are Blocked

Common misconception. The browser can still *send* a cross-origin request (`app.example.com` → `api.example.com`). The real question SOP guards is: **can JavaScript read the response?** That's what CORS governs.

## How CORS Grants Permission

```text
Server responds: Access-Control-Allow-Origin: https://app.example.com
                              ↓
Browser compares it to the page's own origin
                              ↓
Match → JS can read the response. No match/missing header → JS is blocked.
```

The request can still reach the server either way — this is why an API "works fine in Postman" but fails in the browser: Postman doesn't enforce SOP/CORS at all.

> **Interview nugget:** CORS is enforced by the browser; the server only supplies the policy, via response headers.

## Three Separate Questions

1. Will the browser send the request?
2. Will the browser attach cookies to it?
3. Will the browser let JS read the response?

These are independent — don't conflate them.

## Credentialed Requests

```js
fetch("https://api.example.com/me", { credentials: "include" })
```

This tells the browser to attach cookies on a cross-origin request (still subject to cookie rules). If the frontend also needs to *read* that response, the server must send both:

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
```

`Access-Control-Allow-Origin: *` is not valid for credentialed requests — the origin must be named explicitly.

## The Mental Model

```text
                Browser
                   │
        ┌──────────┴──────────┐
        │                     │
   Cookie rules            CORS/SOP
"Can I send credentials?"  "Can JS read the response?"
        │                     │
        └──────────┬──────────┘
                    ▼
                   API
```

Separately, on the server side: **Authentication** = "who are you?", **Authorization** = "are you allowed to do this?" — a different layer entirely from either browser-side check above.

## The Full Flow

```text
fetch("https://api.example.com/orders", { credentials: "include" })
  from https://shop.example.com

1. Different origin?             → yes
2. Cross-origin request allowed? → browser sends it regardless; CORS governs reading
3. Attach cookies?                → per credentials mode + cookie rules
4. Server receives request, responds with data + CORS headers
5. Browser checks the CORS response headers
6. Allowed  → JS gets the response
   Not allowed → JS is blocked from reading it
```
