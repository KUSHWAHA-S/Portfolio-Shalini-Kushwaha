## Status Code Categories

The first digit tells you the broad category:

| Range | Meaning |
| --- | --- |
| 1xx | Informational |
| 2xx | Success |
| 3xx | Redirection |
| 4xx | Client-side/request problem |
| 5xx | Server-side problem |

The ones worth knowing well: `200 201 204` · `301 302 307 308` · `400 401 403 404 409 422 429` · `500 502 503 504`

## 2xx — Success

**200 OK** — the request succeeded. `GET /products/123 -> 200`

**201 Created** — a resource was created, e.g. `POST /users -> 201`. The response often includes the newly created resource.

**204 No Content** — succeeded, but there's no response body. Common on `DELETE /users/123 -> 204`.

## 3xx — Redirection

**301 Moved Permanently**, **302 Found** (temporary), **307 Temporary Redirect**, **308 Permanent Redirect** — the 307/308 pair guarantees the request method is preserved on redirect, unlike 301/302 which historically allow clients to switch to `GET`.

## 4xx — Client Errors

**400 Bad Request** — the request is malformed or invalid, e.g. `{ "age": "hello" }` when the API expects a number, or malformed JSON.

**401 Unauthorized** — despite the name, think *authentication* is missing or invalid: no token, expired token, invalid session. `GET /profile -> 401` means "I don't recognize you."

**403 Forbidden** — the user *is* authenticated, but isn't allowed to do this (e.g. a normal customer hitting an admin endpoint).

> **Interview nugget:** 401 = "who are you?" 403 = "I know who you are, but you're not allowed." This distinction comes up constantly.

**404 Not Found** — the resource doesn't exist. `GET /products/999999 -> 404`

**409 Conflict** — the request conflicts with current state, e.g. `POST /users` with an email that already exists.

**422 Unprocessable Content** — the server understands the request but the data fails validation (`{ "email": "not-an-email", "age": -100 }`). The 400 vs. 422 split isn't applied consistently across APIs — don't treat it as a hard rule.

**429 Too Many Requests** — rate limiting. The server is saying "slow down," often with a `Retry-After: 60` header.

## 5xx — Server Errors

**500 Internal Server Error** — something broke on the server: a bug, crash, or unexpected failure.

**502 Bad Gateway** — in `Browser -> Load Balancer/Proxy -> API Server -> another service`, the gateway got a bad or invalid response from the upstream service.

**503 Service Unavailable** — the service can't handle the request right now: overloaded, in maintenance, or a dependency is down.

**504 Gateway Timeout** — the gateway waited too long for an upstream response (`Gateway -> API -> Database`, and the database took too long).

> **Interview nugget:** 502 = the gateway got a bad response. 504 = the gateway got no response in time.

## HTTP Is Stateless

```text
Request 1: GET /profile
Request 2: GET /orders
```

HTTP itself has no built-in concept of "these two requests are the same user." The application has to supply that context explicitly — `Cookie: session=abc123` or `Authorization: Bearer eyJ...` — which is exactly why authentication mechanisms exist (see the Authentication notes).

## HTTP vs HTTPS

```text
HTTP:  Client ───── HTTP ─────> Server
HTTPS: Client ── TLS + HTTP ──> Server
```

HTTPS = HTTP transmitted through TLS, adding confidentiality, integrity, and server authentication.

## HTTP Is Not "The Internet"

HTTP is one application-layer protocol among several, sitting on top of lower-level networking layers:

```text
Application
     |
    HTTP
     |
    TLS
     |
  TCP/QUIC
     |
     IP
     |
  Network
```

## The Complete Request Journey

```text
Browser
   │ URL
   ▼
DNS ── resolves to an IP
   ▼
Connection ── TCP/QUIC handshake
   ▼
TLS ── encrypted channel established
   ▼
HTTP Request ── method, URL, headers, body
   ▼
Server ── authentication → authorization → business logic → database
   ▼
HTTP Response ── status, headers, body
   ▼
Browser
```
