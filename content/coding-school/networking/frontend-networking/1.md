## The Problem: Stale In-Flight Requests

Typing into a search box fires a request per keystroke:

```text
r -> re -> rea -> reac -> react
```

By the time `react` is typed, the earlier four requests' results are useless. We want to stop caring about them — that's cancellation.

## `AbortController`

```js
const controller = new AbortController()

fetch("/api/search?q=react", { signal: controller.signal }).catch((error) => {
  if (error.name !== "AbortError") throw error
})

controller.abort() // cancels the request above
```

## The React Pattern

```jsx
useEffect(() => {
  const controller = new AbortController()

  async function search() {
    try {
      const response = await fetch(`/api/search?q=${query}`, {
        signal: controller.signal,
      })
      setResults(await response.json())
    } catch (error) {
      if (error.name !== "AbortError") console.error(error)
    }
  }

  search()
  return () => controller.abort()
}, [query])
```

Every time `query` changes, React runs the cleanup first — aborting the in-flight request for the *previous* query before starting a new one.

## Cancellation Doesn't Mean the Server Stopped

Aborting on the client only means the browser stops waiting for the response — it doesn't guarantee the server rolled anything back. Fine for `GET /search`; risky for `POST /orders`, where the order may already be created by the time you abort. This is exactly why idempotency matters for mutations, not just cancellation.

## Cancellation vs. Timeout vs. Debouncing vs. Deduplication

Four different problems that get confused with each other:

| Technique | Solves |
| --- | --- |
| Debouncing | Don't *start* a request until typing pauses |
| Deduplication | Don't start the *same* request twice |
| Cancellation | Stop a request that's in flight but no longer needed |
| Timeout — `AbortSignal.timeout(5000)` | Stop waiting if a request takes too long, regardless of relevance |

They compose: debounce → start a request → query changes → cancel the previous one.

## Race Conditions

> Network responses don't necessarily arrive in the order the requests were sent.

```text
Request A (userId=1) starts first,  finishes last
Request B (userId=2) starts second, finishes first
```

With no guard, `A`'s late response overwrites `B`'s correct state — the UI shows user 1 while `userId` is actually 2.

## Three Fixes

**1. Cancel the stale request** — the `AbortController` pattern above.

**2. Ignore stale responses explicitly** — track which request is current:

```js
let requestId = 0

async function loadUser(id) {
  const current = ++requestId
  const data = await fetch(`/api/user/${id}`).then((r) => r.json())
  if (current !== requestId) return // a newer request started; drop this one
  setUser(data)
}
```

**3. Use a data-fetching library** (React Query/TanStack Query) — query identity, caching, deduplication, and cancellation are handled for you. Still worth understanding the underlying problem even when a library absorbs it.

## Not Just React

Same failure mode wherever multiple async operations can finish out of order: autocomplete, route transitions, pagination, filtering, optimistic updates, WebSockets.

## Interview-Ready Definition

> A race condition in frontend networking is when multiple in-flight async operations complete in a different order than they were started, letting a stale response overwrite newer state.
