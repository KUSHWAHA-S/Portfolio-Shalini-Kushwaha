## Why Methods Exist

The URL says *which* resource. The method says *what* to do with it.

```text
/products/123
   GET    -> read
   PATCH  -> modify
   DELETE -> remove
```

## The Methods to Know

| Method | Purpose | Safe? | Idempotent? |
| --- | --- | --- | --- |
| GET | Read | Yes | Yes |
| HEAD | Read metadata only | Yes | Yes |
| OPTIONS | Ask capabilities | Yes | Yes |
| POST | Create/process | No | Generally no |
| PUT | Replace | No | Yes |
| PATCH | Partial update | No | Depends |
| DELETE | Delete | No | Yes |

## Safe

"Safe" doesn't mean *can't fail* or *is secure* — it means **the client isn't requesting a state-changing operation**. `GET /products` can still 500; it's still safe. This matters because crawlers, proxies, and browsers treat safe methods differently — never hide a delete behind a `GET`.

## Idempotent

> Repeating the same request has the same intended effect on server state as making it once.

**Idempotent ≠ identical response.** `DELETE /users/42` returns `204` the first time and `404` the second — different responses, but the intended end state (`user doesn't exist`) is the same either way. Still idempotent.

- **PUT** — replaces the resource. Same body sent 10 times → same final state. Idempotent.
- **DELETE** — same reasoning. Idempotent.
- **POST** — usually creates a *new* resource every time (`POST /orders` → order #1001, then #1002, then #1003). Generally **not** idempotent.
- **PATCH** — depends entirely on the operation. `{ "city": "Mumbai" }` repeated → same result, idempotent. `{ "operation": "increment", "balance": 100 }` repeated → `+100` each time, **not** idempotent. No blanket guarantee.

## PUT vs PATCH

```text
PUT   -> "here is the new representation" (replace)
PATCH -> "change these parts"             (partial update)
```

## The Real Problem: Retrying Non-Idempotent Requests

```text
Browser -> POST /payment -> server charges card -> response lost to a network failure
```

The client can't tell if the request succeeded. Blindly retrying a `POST` can double-charge. Fix: an **idempotency key**.

```http
POST /payments
Idempotency-Key: 7f8a9c...
```

The server stores the key against the result; a repeated request with the same key returns the original result instead of processing again — the standard pattern in payment APIs.

## HEAD & OPTIONS

**HEAD** — same as GET but headers only, no body. Useful for checking `Content-Length`/`ETag` without downloading. Safe and idempotent.

**OPTIONS** — asks what methods/headers are allowed. This is what powers CORS preflight requests (`Access-Control-Allow-*` headers in the response).

## Cacheability Is a Separate Axis

Safe, idempotent, and cacheable are three independent questions — not synonyms.

| | Safe | Idempotent | Cacheable |
| --- | --- | --- | --- |
| `GET /products` | Yes | Yes | Yes |
| `POST /orders` | No | No | Uncommon |
| `PUT /users/42` | No | Yes | Rarely cached |
| `DELETE /users/42` | No | Yes | — |

`GET` is generally cacheable; `POST` *can* be under specific rules, but it's rare — don't reduce this to "GET caches, nothing else does."

## Why This Matters for Frontend

Networks fail silently — a response can be lost even after the server succeeds, leaving an **ambiguous outcome**. Safe/idempotent requests (GET, PUT, DELETE) are generally safe to retry. Non-idempotent ones (POST for payments/orders) aren't — use an idempotency key, or confirm state before retrying.

It's also why libraries like React Query/SWR **deduplicate** requests: five components asking for `GET /api/user` at once become one request with a shared result, not five.

## Conditional Requests (preview)

```http
If-None-Match: "abc123"
```

If the cached version is still valid, the server replies `304 Not Modified` instead of resending the full response — the core mechanism behind HTTP caching, covered separately.

## Mental Model

```text
HTTP METHODS
   READ    -> GET
   MODIFY  -> PUT / PATCH
   ACTION  -> POST
   DELETE
```

For any request, ask three independent questions: is it **safe**? Is it **idempotent**? Is it **cacheable**?
