## The Moving Parts

| Concept | What it answers |
| --- | --- |
| Cookie | Where/how the browser stores and sends a value |
| HttpOnly | Can JavaScript read the cookie? |
| CSRF token | Can we tell legitimate app requests from cross-site ones? |
| Session | Server-side authentication state |
| JWT | Self-contained, signed token format |
| Stateful | Server remembers authentication state |
| Stateless | The request carries enough info to authenticate without a lookup |
| Access token | Credential for normal API requests |
| Refresh token | Credential used to obtain new access tokens |

These are independent dimensions — mix and match, not one spectrum.

## Four Common Architectures

**A. Stateful session** — `HttpOnly cookie (session_id)` → server looks it up in a session store → `user`. Fully stateful.

**B. Stateless JWT** — `Authorization: Bearer <JWT>` → API verifies signature + expiry locally → `user`. No lookup needed.

**C. JWT in an HttpOnly cookie** — still stateless to verify, but since the cookie is sent automatically, CSRF is back on the table.

**D. JWT access + stateful refresh** (the common hybrid) — access requests verify the JWT locally (stateless); refresh requests hit a refresh-token store to validate/rotate (stateful). Most production systems land here.

## Why Two Tokens

A single long-lived JWT (say, 30 days) is a 30-day liability if it's stolen. Split the job instead:

```text
Access token   — short-lived (minutes), used on every request
Refresh token  — long-lived (weeks/months), used rarely
```

Access token = disposable credential. Refresh token = the valuable one — protect it accordingly.

## What Each Token Actually Does

**Access token** — proof of identity with an expiry: `{ sub: "42", exp: ..., scope: "read:orders" }`. Sent as `Authorization: Bearer <token>` on every request; the API checks signature, expiry, issuer, audience, and scope, then trusts it — no DB hit.

**Refresh token** — sent only to `POST /auth/refresh`, never to normal endpoints. Its only job is minting a new access token.

## Where They Live

```text
Access token   -> JavaScript memory (not localStorage/sessionStorage)
Refresh token  -> HttpOnly + Secure cookie
```

The access token doesn't need permanent storage — it can live in a plain JS variable and simply disappear on page refresh, because the refresh token (in its HttpOnly cookie) can mint a fresh one on load.

## The Full Flow

```text
Login (POST /login)
   -> server sets refresh token as an HttpOnly cookie
   -> server returns the access token in the response body

Normal request
   -> Authorization: Bearer <access token>   (from memory)

Access token expires -> API returns 401

Client calls POST /auth/refresh
   -> browser auto-sends the HttpOnly refresh cookie
   -> server validates it, returns a new access token
   -> client retries the original request with the new token
```

The user never notices.

## The Refresh Queue

If several requests 401 at once, don't fire a refresh per request:

```text
request 1 ┐
request 2 ├─ 401 ──► ONE refresh call ──► new token ──► retry all 3
request 3 ┘
```

## Refresh-Token Rotation

Each use of a refresh token issues a new one and invalidates the old:

```text
old refresh token -> used once -> invalidated
new refresh token -> stored, replaces the old cookie
```

This limits how useful a stolen refresh token is — and a reused, already-invalidated token is a signal of theft.

## Storage: the Real Distinction

Not `localStorage` vs `sessionStorage` — both are **JavaScript-readable**, so both are equally exposed to XSS:

```js
localStorage.getItem("accessToken")   // readable by any script on the page
sessionStorage.getItem("accessToken") // same problem
```

The real line is **JS-readable storage vs. HttpOnly cookie** (browser-managed, invisible to `document.cookie`). HttpOnly stops an XSS payload from *extracting* the credential — it doesn't stop injected JS from making authenticated requests while it's still running on the page. It reduces the blast radius; it doesn't neutralize XSS.

## Two Popular Browser Designs

**A — Access token in memory, refresh token in an HttpOnly cookie.** The access token never touches persistent storage; the refresh token is invisible to JS.

**B — Both tokens in HttpOnly cookies.** Very convenient — the browser handles everything automatically — but since cookies are auto-attached, CSRF protection becomes mandatory.

Either way: a cookie that's sent automatically needs a CSRF answer. A token attached explicitly via a header drops that risk — in exchange for needing somewhere (memory) to hold it.

## Reading a Real Codebase

```text
accessToken / refreshToken / interceptor / 401 / retry / queue
   -> access+refresh token flow with a refresh queue

HttpOnly / Set-Cookie / SameSite / CSRF
   -> credentials are carried automatically by the browser — cookie/CSRF model

sessionId / Redis / sessionStore
   -> authentication state lives on the server — classic session auth
```

**The core idea:** JWT + refresh tokens didn't eliminate server-side state — they just moved it. Stateless access verification plus stateful refresh-token management is the standard modern hybrid, not a contradiction.
