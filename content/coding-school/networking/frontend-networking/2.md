## Three Questions Before Retrying

Blindly retrying every failure is dangerous. Treat it as three separate decisions: **should** I retry, **how long** should I wait, and **how many** times?

## What's Worth Retrying

| Situation | Retry? |
| --- | --- |
| `400 Bad Request` | No |
| `401 Unauthorized` | Not blindly — refresh/re-auth instead |
| `403 Forbidden` | No |
| `404 Not Found` | No |
| `409 Conflict` | Depends |
| `422 Validation` | No |
| `429 Too Many Requests` | Yes, respecting `Retry-After` |
| `500 / 502 / 503 / 504` | Often |
| Network failure / timeout | Often |

Client/validation errors are permanent — retrying won't fix them. Transient failures (5xx, network blips) might resolve on their own.

## Retry Storms

If a struggling server sends `503` to 1,000 clients and they all retry immediately, load spikes further and makes things worse. Fix: wait before retrying, and don't make everyone wait the *same* amount of time.

## Exponential Backoff + Jitter

```text
delay = min(maxDelay, base * 2^attempt)
```

With `base = 500ms`: `500ms, 1s, 2s, 4s, 8s`, capped at some `maxDelay` (e.g. `10s`) so it doesn't grow forever. Add **jitter** (randomness) on top of that delay, or 10,000 simultaneous clients all retry in the same synchronized burst instead of spreading out over time.

## Respect `Retry-After`

On `429`, the server may tell you exactly how long to wait:

```http
Retry-After: 5
```

Use that instead of guessing your own delay.

## A Conceptual Implementation

```js
async function fetchWithRetry(url, retries = 3) {
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      const response = await fetch(url)
      if (response.ok) return response
      if (!isRetryable(response.status)) throw new Error(`HTTP ${response.status}`)
    } catch (error) {
      if (attempt === retries) throw error
    }
    await sleep(Math.min(1000 * 2 ** attempt, 10000))
  }
}
```

Production code also needs abort-signal handling, `Retry-After` support, jitter, and proper error classification — this is the shape, not the whole thing.

## Retrying Mutations Is a Different Problem

`GET` is safe to retry — it's idempotent by design. `POST /orders` isn't: if the response is lost after the server already created the order, a blind retry can create a second one. This is exactly what an **idempotency key** solves (see the Authentication notes) — you retry the *request*, not the *side effect*.

## Retry Composes With Other Patterns

**Retry-on-401 needs the refresh queue, not a retry loop.** Naively retrying `GET /profile → 401 → GET /profile → 401 → ...` never succeeds, because the *token* is the problem, not the network — no amount of retrying fixes an expired token. The correct move is to refresh once, then retry. But if several requests hit `401` at the same moment, refreshing once *per request* is wasteful and can itself race — two refresh calls in flight can invalidate each other depending on the server's rotation logic. That's exactly why retry-on-401 routes through the refresh queue (Authentication Day 1): coalesce every failing request behind a single refresh, then retry each one with the new token.

**A retry is a second async operation, and second operations can race.** If request A fails and gets retried while request B (for the same piece of state) succeeds in the meantime, you now have two in-flight responses that can resolve in either order — the exact setup the race-conditions note describes. Retry logic doesn't get to ignore that: a retried response needs to respect whichever guard (request ID, cancellation) is already protecting that state, or it can silently overwrite something newer just by arriving late.

## When Not to Retry

User cancellation, `400`/`403`/`404`/`422`, business-rule failures, malformed requests — and be extra careful with `POST /payment`, `POST /order`, `POST /transfer` unless there's an idempotency mechanism backing them.

## A Realistic Retry Policy

```text
Response/Error
  ├── Success           → return
  ├── 400/403/404/422   → don't retry
  ├── 401               → refresh/auth flow
  ├── 429               → respect Retry-After
  ├── 500/502/503/504   → exponential backoff + jitter
  └── network/timeout   → retry per policy
```

## The Reasoning to Remember

```text
Request fails
     │
Should retry? → No  → stop
             → Yes → how long? → exponential backoff + jitter → retry limit

For mutations: is the operation idempotent?
  No → needs an idempotency strategy before it's safe to retry
```
